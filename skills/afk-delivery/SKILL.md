# 自主任务交付

将任务整理为按需组合的六部分：可度量目标、必要背景、执行循环、退出条件、通过条件、交付产物。优先补齐目标和通过条件，不把主观愿望改写成伪精确分数。

## 检查可执行性

确认当前环境确有访问入口、实现工具与校验能力。明确“客观达到标准”如何被观察，不以 Agent 自述替代验证。设计合理性、解决能力与校验能力都可能成为短板。

审美或产品体验需要人的判断时，主体工作可自主完成，再交付可审阅成果；不要在未产生可审阅结果前反复征求许可。需要人类判断的条件不能自行判为通过。

## 执行循环

按当前证据计划、实现、验证；未通过则定位差距并修正。沿用已经获得的授权，普通可逆操作不新增审批门槛。限制修改范围，完成约定目标后停止。

达到通过条件时交付结果、运行证据和实际限制。遇到无法访问的必要环境、关键需求冲突或连续尝试没有新增证据时，记录尝试、当前状态与所需输入。重试次数或成本预算由任务风险和用户约束决定，不设置通用固定轮数。

不假定 CodeBuddy IDE 存在 `/goal` 命令或无人值守调度能力。在当前会话能力范围内持续执行；若会话中断，保存状态供恢复。需要长期后台调度时先核实环境支持。

仅设计 AFK 时产出可执行任务说明；用户同时要求执行时才运行。可与同包 `vertical-slice-build` 组合，但不得把阅读示例理解为执行示例中的外部动作授权。
